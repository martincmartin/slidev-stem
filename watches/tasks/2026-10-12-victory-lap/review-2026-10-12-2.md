## Worthwhile improvements

### 1. P3: Make address restoration expose its complete result

**Evidence:** `watch/explorer/explorer.ts:472–517`.

`loadAddress(): Camera | null` also changes:

- Shown pieces.
- Speed and its control.
- Motion pose and its control.
- Dimming pose and map.
- Guide visibility.

It can return `null` after applying those changes. The signature therefore describes only one part of its effect.

A reader must inspect the whole function to understand startup:

```ts
let camera = loadAddress() ?? fitted(...);
restart();
shownChanged();
```

**Preferred change:** Decode the address into a value, then apply that value explicitly.

For example:

```ts
const restored = decodeAddress(location.hash, poses, pieces);
applyAddress(restored);
```

Keep camera validity separate from other valid address fields. This preserves the current partial-restoration behavior while making it visible.

**Alternatives, ranked:**

1. **Pure decode plus explicit apply.** Best for readable data flow and focused tests. It adds one small value type.
2. **Rename to `restoreAddress()` and document every effect.** Smaller change, but testing remains tied to the DOM.
3. **Introduce a complete explorer controller.** More machinery than this page currently needs.

There is also a small selection-boundary defect at `explorer.ts:413`. `Number("")` selects pose index zero. Choosing the placeholder therefore selects the first pose.

Handle the empty value before converting it to an index.

### 2. P3: Represent motion choices without duplicated speed state

**Evidence:** `watch/explorer/explorer.ts:376–385`, `394–399`, `425–429`, and `492–496`.

The page stores both `speed` and `movedBy`. When a pose is active, its speed already exists in `movedBy.state.lapse`.

Three update paths must keep the pair consistent: speed selection, pose selection, and address restoration. The current code does this, but each new path inherits that obligation.

A small variant makes the contract clearer:

```ts
type ExplorerMotion =
  | { kind: "free"; speedUp: number }
  | { kind: "pose"; pose: DeckPose };
```

Derive the selected speed and `WatchModelState` from that value.

This also improves the names. `motionPose` and `speedUp` communicate more than `movedBy` and `speed`.

**Alternatives, ranked:**

1. **Use the two motion variants.** Prevents inconsistent combinations with modest code.
2. **Keep the current pair behind one update function.** Less type change, but the invariant remains conventional.

Keep motion and dimming choices separate. The documented controls intentionally change them independently.

The cached dim map has one setter and avoids resolving it every frame. That cache has a clear purpose and can remain.

### 3. P3: Make deck safety tests inspect resolved visibility

**Evidence:** `watch/deck.test.ts:20–28` and `watch/state.ts:542–553`.

The new `shows()` helper repeats the rules for:

1. A named piece.
2. Standalone `all`.
3. `all` inside a list.

The production resolver already implements those rules. The safety tests should inspect what the stage will actually show.

Resolve `stageState()` once for each position. Check its shown meshes against the relevant `Piece` object.

This improves the question from “does this second interpretation include the piece?” to “will the rendered state include the piece?”

**Alternatives, ranked:**

1. **Inspect resolved meshes.** Best fit for these integration safety tests.
2. **Expose a shared piece resolver.** Useful if another production caller needs piece membership.
3. **Keep a second name-expansion implementation.** Lowest immediate effort, but another place must change when syntax changes.

Keep independent assertions of `all` semantics in `state.test.ts`. Those tests serve a different purpose.

## Optional clock contract improvements

These are useful follow-ups, not evidence of a current visual defect.

### Document the numerical accuracy choice

**Evidence:** `watch/lapse.ts:19–20`, `45–63`, and `97–111`; `watch/lapse.test.ts:15–30`.

The clock integrates a speed ramp using 64 trapezoids. It then interpolates between accumulated samples.

The code explains the method, but not the acceptable error or why 64 steps are sufficient. Current tests cover monotonicity and continuity, rather than integration accuracy.

I compared the ramp against a dense numerical reference:

$$
a(t)=\int_0^t \bigl(k(s)-1\bigr)\,ds.
$$

The reference used the existing `ease()` function, logarithmic speed interpolation, and 32,768 trapezoids. The ramp was 1× to 1440× over 2.5 seconds.

| Table steps | Largest sampled difference in time ahead |
| ---: | ---: |
| 64 | 0.661 s |
| 128 | 0.165 s |
| 256 | 0.0414 s |

The current clock’s endpoint difference was much smaller: approximately 0.000141 s. Most transient error comes from interpolation between samples.

These are mechanism seconds, not presentation seconds. The measurements are numerical comparisons, not visibility measurements or proven global error bounds.

**Ranked options:**

1. **Keep 64 steps and record an accepted error budget.** Add a reference-based regression if this approximation matters to later changes.
2. **Increase the steps after defining a tighter requirement.** The table construction grows linearly with the step count.
3. **Replace the integrator.** No present evidence justifies that extra complexity.

I would keep the current algorithm until a requirement establishes that it needs greater accuracy.

### State the clock’s input contract

`LapseClock.show()` and `jump()` are public, but rely on callers for valid speeds and durations.

Focused invalid-input probes accepted zero speed, `NaN`, negative duration, and infinite duration. Some produced invalid accumulated time.

Current deck speed inputs are checked by `watchState()`. This is therefore a module contract concern.

Document or check finite times, speed-ups of at least one, and finite nonnegative durations. Also explain that the clock retains only its current change, rather than complete history.

Marking `Change` fields and its sample array read-only would match the implementation: each change is constructed once and replaced as a whole.
